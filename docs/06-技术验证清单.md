# 技术验证清单（实施前必须实测）

原则（出自 omo 源码的教训）："typecheck 过了"不等于能用。所有与引擎交互的能力必须对真实 senpi 实测。以下按优先级排列，验证环境：本机装 `omo-ai@beta`（或直接依赖 @code-yeongyu/senpi@2026.10.10）。

## P0：决定架构成立与否

1. **RPC 基本链路**：spawn `senpi --mode rpc` → 官方 RpcClient → 建会话 → 发 prompt → 收 AgentSessionEvent 流 → 消息分页读取 → abort。跑通即事件桥成立。
2. **权限/表单往返**：extension_ui_request（select/confirm/input/editor）转发给 web 宿主并应答的完整回路；同时验证 auto-answer 兜底行为（无宿主应答时是否阻塞）。
3. **omo 扩展在纯 RPC 模式下的存活**：omo 的 task/team/todo 工具、规则注入在无 TUI 环境下是否照常注册和工作；omo-senpi 的 status UI 在 RPC 模式降级为 widget 字符串数组，确认其可推送给 web 前端渲染。
4. **数据一致性前提**：确认宿主 spawn 时的 HOME/cwd 传导——web 会话与终端 `omo` 命令的会话写入同一个 session store，终端 resume 列表可见 web 创建的会话（反向亦然）。

## P1：决定功能清单里的核对项

5. **会话/项目查询能力**：senpi session store 能否列出全部会话（含 title/agent/时间/token 统计）、按项目过滤、恢复历史——对齐 docs/05 的 opencode 参照行为。
6. **todo 事件与图片 part**：todo 工具结果的结构化事件源；消息中 image part 的读取路径。
7. **usage 数据源**：token/费用的事件或查询接口（对应底部状态条）。
8. **agent/model 列表**：动态枚举可切换的 agent 与 model。
9. **消息编辑重发/分叉**：引擎是否支持（不做则该项功能从清单降级）。
10. **会话导出**：`--export HTML` 在 RPC/SDK 路径下的可用性。

## P2：优化与备选路径

11. **并发锁语义**：同一活动会话被两个进程（TUI + web）同时打开的行为——决定"别两边同时驾驶"约束的实现方式。
12. **`connectWebViewService` 能力边界**：senpi 包导出的 webview 桥是干什么的，能否复用（可能省自建事件桥的部分工作）。
13. **`./client` CBOR 远程客户端**：transport-neutral 远程会话客户端的成熟度；若可用，宿主可免于自管子进程。
14. **subagent 事件订阅粒度**：set_subagent_subscription 的 progress/events 两档实测（将来做编排可视化的数据源，MVP 不做但记录）。
15. **流式 markdown 渲染稳定性**：长流式输出下 react-markdown + Shiki 的渲染抖动/性能（前端侧验证，手机视口 390x844）。

## 验证产出要求

每项验证记录：命令、版本号（senpi/omo-ai 精确版本）、观察到的事件样本（JSON 摘录）、结论。存 `docs/verification/` 目录，作为后续 EngineAdapter 实现的依据。
