- 设计：多客户端同会话并发（多 webui 标签/窗口同会话 + CLI 与 webui 同会话同时处理）（状态：记录，2026-10-23 提出；现状当日核实）：用户实录——如果开启多个 webui 打开同一个会话，或者命令行中也在处理这个会话，该怎么办
  - 当日核实（2026-10-23，代码实证）：
    - 多 webui 标签同会话（同一 webui 服务）：现状基本安全——SSE 每客户端单流多路复用全扇出（各标签都收到同会话事件）；发送侧单驱动纪律兜底（引擎 409 already_processing → 自动转排队 steer/followUp，交叉发送互相排队而非并发写）；未读计数「任一设备查看即清零」已按多设备设计；草稿各标签独立。已知语义缺口：排队条只在发起标签可见（另一标签靠 queue 对账可见）、中断操作无跨标签协调提示
    - CLI 与 webui 同会话：**两个引擎进程同一会话**——webui 引擎按项目路径由 process-manager 键控拉起，CLI（omo native）是管理器之外的独立进程；两进程各持会话内存态、同 append 一个 JSONL 文件；引擎侧并发语义（文件锁/互斥/内存态漂移）未实证——风险：一方写入对另一方不可见（内存态不重读盘）、交错追加、状态分叉；webui 现有重同步仅针对自身服务重启（游标回退），非外部进程写入
    - 引擎侧锁机制初查：omo-ai dist 未见 flock/lockfile 痕迹（快速 grep，未深查）
  - 待讨论（届时定）：a. 同会话互斥——引擎/文件级锁或会话占用检测（webui 打开 CLI 正在处理的会话时明示/拒绝）；b. 只读跟随模式——检测外部进程活跃时该会话转只读观察（需引擎侧通道，可能无解，需 spike）；c. 多标签语义补齐（排队条跨标签同步/中断操作协调提示）；d. 最小立场：先 spike 实证两进程同会话实际行为（CLI 写一条 webui 是否可见/JSONL 是否损坏/内存态分叉表现），再定防护层级

- 调研：计划执行无法暂停——omo/ulw-execute 无暂停控制面，口头暂停不持久（状态：记录，2026-10-24 提出；机制当日实证）：用户实录——omo 不支持暂停计划吗，试过很多方式都做不到
  - 当日核实（2026-10-24，引擎 bundle+技能+会话实录实证）：
    - 协议面无暂停：引擎插件（omo.js）与 ulw-execute 技能全文无 pause 命令/帧/API；webui 服务端唯一运行控制端点 = POST /api/sessions/:id/abort（杀当前回合，对「计划」无语义）
    - boulder.json 的 status:"paused" 是 staleness 自动标记而非暂停开关：会话静默超阈值（默认 216e5ms=6 小时，env OMO_BOULDER_STALE_WORK_THRESHOLD_MS 可调）由引擎翻写 paused+stale_since（当前 r7 工作即停在此态，stale_since 2026-10-22T13:21:50Z）；且续跑选取器与技能 Phase 1 规则 4 同口径——active **或 paused** 都是合法续跑候选（「paused」语义=「静默待恢复」非「已暂停」）
    - 续跑钩子按回合自动再注入：会话 agent_settled/idle 时钩子发 omo-senpi:ulw-execute-continuation 注入（triggerTurn followUp，idleCoordinator 优先级 3），注入提示明文「Do NOT ask whether to continue — the contract is auto-continue」；技能 Phase 5 同文「继续下一个复选框，不要问是否继续」——编排者契约内无停机点
    - 用户实录（2026-10-22 11:33 会话 eb1be95f）：两次指令「暂停计划」「暂停计划，不要继续执行了」后编排者口头承诺「已完全暂停…恢复时说继续计划即可」「本轮不执行：不派发 F2、不动 main」——纯模型自觉，无持久化暂停位；事实上 r7 后续波次于 10-23 凌晨继续落地（main 推进至 0d98386 终验前置微修包）——口头暂停不可靠不持久
    - 现状可用的「停」手段（均为间接/手工，同日补充实证）：①设置→项目区「重启引擎」（POST /api/projects/restart，routes-project.ts:186→restartProject，SIGTERM→SIGKILL 杀引擎进程）——webui 侧最接近 CLI 退出的事实刹车：续跑钩子随进程死、后台子代理随进程终止或被孤儿收割器清理、会话 JSONL 与 boulder 状态保留，下次在该会话说话即恢复续跑（近似暂停/恢复）；副作用=整个项目引擎全断，运行中其他会话工作同殃；②逐回合 abort（挡不住下次唤醒的续跑注入）；③手工改 .omo/boulder.json 该工作 status 为非 active/paused 值——选取器返 null、钩子永不注入，精准且持久，但无文档无工具支撑；④让会话静默等 staleness 翻 paused（该会话任何唤醒仍会续跑，后台子代理完成通知即触发，基本不构成刹车）
    - 定责（同日补充，用户追问 CLI 可退出 vs webui）：暂停协议缺失属引擎（上游 omo-ai）设计层，CLI 同样无暂停命令，非 webui 独有缺陷；但 webui 部署形态放大了它——CLI 退出=进程死=事实刹车，webui 引擎为服务端常驻进程，关浏览器/关会话页均不刹车，现有 abort 仅杀单回合挡不住续跑注入——「无等价刹车入口」是 webui 侧可改进空间（修复方向 c 暂停/恢复钮即补此层）
  - 修复方向（届时定）：a. 暂停控制面——boulder 状态机补显式 paused 写入口（引擎协议帧或命令，如 /pause-plan），选取器区分「用户暂停」与「staleness 暂停」两态（前者不续跑仅可显式恢复）；b. 续跑注入前检查持久暂停位，或注入模板补「用户已声明暂停则保持暂停直至显式恢复」契约条款；c. webui 侧计划运行中会话顶栏加暂停/恢复钮（走新协议面）；d. 最小改动候选：纯提示层（技能补暂停节+注入模板补条款，无协议改动，可靠性次之）
  - 排查抓手：无需复现——bundle 逻辑与用户实录已实证；实施前 spike 引擎 sendMessage triggerTurn 的阻断点（可否按状态拒绝注入）
